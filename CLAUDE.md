# Dead Blocks — project notes for Claude Code

A first-person 3D voxel **zombie survival craft** game. The design blends three games:
- **Minecraft**: a block world you can mine and build in, plus crafting.
- **7 Days to Die**: zombies smash through blocks, with a Blood Moon horde every 7th night.
- **ARK**: wildlife to hunt now, with taming and creatures planned.

The owner (Marcus) playtests on Windows and gives feedback. Each round of work should end with a new Windows build he can run.

## Tech
- **Godot 4.7.2 (standard build, not .NET)**, using the **Forward+** renderer (OpenGL fallback; since the graphics overhaul, `docs/V-plan.md`) and **Jolt Physics**. The game runs physics at 60 ticks/s; server mode runs it at 30 (decided in M0, see DESIGN.md).
- Everything is GDScript plus shaders in `shaders/` (sky, smooth terrain, blocks, leaves, plants). **Art files** (since 0.11.0) live in `assets/`: CC0 photo textures from ambientCG combined by `tools/make_textures.py SOURCE_DIR` into texture strips (`assets/textures/*`, imported as Texture2DArrays by their `.import` files), and since 0.12.0 Quaternius' CC0 animated models in `assets/models/` (zombies, survivors for other players, the pig for the boar; `rig.gd`). Credits in `assets/CREDITS.md`. Item icons, plant pictures and crack overlays are still painted in code (`tex.gd`), and every sound is synthesized at startup (`sfx.gd`). The dedicated-server export presets exclude `assets/*`: server code must never `preload` anything in `assets/` (use `load()` in client-only code).
- `main.tscn` is the only scene. `game.gd` builds every other node in code.
- Indent with tabs and use typed GDScript where possible.

## Run / test / build
Replace `godot` with the path to the Godot 4.7.2 executable (on Windows, `Godot_v4.7.2-stable_win64_console.exe` shows console output).

- **Play from the editor:** open `project.godot` in Godot and press F5.
- **The test gate — run before every commit:** `GODOT=<path> ./tools/test_all.sh` (about 30 minutes; `--quick` skips the exports, the Pi checks and the benchmark, about 15 minutes; run it detached, not as a 30-minute-limited background job). It runs the autotest, the save test, the mesh test (no holes in the drawn world), the region-order test both ways, the zombie-type test, the multiplayer test, the exports, the PC-vs-Pi terrain check (arm64 export under `qemu-aarch64-static`), the multiplayer test against the arm64 server under qemu, the Pi package test, and a short benchmark. A stage fails on a FAIL line, **any `ERROR`/`SCRIPT ERROR` line**, a crash, a timeout or a missing DONE line. Logs: `build/test_logs/`.
- **Automated playtest (headless):**
  `godot --headless --path . -- --autotest --seed=4242`
  It presses Play solo with a new world "autotest" in the game's data folder (the player's own solo world is left alone) on a server started in the background, prints AUTOTEST PASS/FAIL lines and ends with `AUTOTEST DONE fails=N`. Seed 4242 is the reference seed and should give `fails=0`.
- **Screenshots:** add `--shots=<absolute dir>` and run with a real renderer instead of `--headless`.
- **Server benchmark:** `GODOT=<path to godot> ./tools/run_bench.sh` (5 setups, about 22 minutes; `BENCH_SETUPS=m1` runs only the 2 M1 server setups, about 9 minutes; add `--bench-secs=8` for a quick check). It runs `-- --bench` once per setup on seed 4242, with a temporary `override.cfg` choosing the physics engine, tick rate and physics thread; the M1 setups add `--server-mode`. It prints a results block and saves it to `bench_results/summary.txt`. A single run: `godot --headless --path . -- --bench --seed=4242 [--bench-secs=60] [--zombies=120] [--explorers=7] [--radius=6] [--only=horde] [--net-clients=8]` (`--net-clients` also builds the updates a server sends that many players). Don't run two benchmarks or other heavy work at the same time, or the timings are meaningless.
- **Builds:** `GODOT=<path> ./tools/build_release.sh` exports `build/DeadBlocks.exe` (Windows), a zipped copy, `build/server/DeadBlocksServer.{arm64,x86_64}` (dedicated-server exports, which start in server mode), and `build/DeadBlocksServer-linux-arm64.zip` (the Pi package; no version in its name, so `update.sh` can fetch `releases/latest/download/` from GitHub). **Release tags must be `v<VERSION>` with `DeadBlocks-<VERSION>-windows.zip` attached**: players' games fetch exactly that to update themselves (`updater.gd`). Needs the 4.7.2 export templates (Editor → Manage Export Templates → Download). The .pck is embedded, so each result is a single file.
- **Multiplayer test:** `GODOT=<path> ./tools/run_nettest.sh` (about 11 minutes; it freezes the server with SIGSTOP to test reconnecting and `kill -9`s it to test saving; `NETTEST_SOAK_S=60` lengthens the building soak and `NETTEST_HORDE_S=120` the Blood Moon soak, both default 20 s; `NETTEST_CRASHES=N` sets the number of crashes, default 3): a local server plus headless bot clients; prints NETTEST PASS/FAIL lines and `NETTEST ALL DONE fails=N`. Logs: `build/test_logs/nettest/`. Pass a server command prefix to test an exported server instead (see the script header).
- **Dedicated server:** `godot --headless --path . -- --server --password=S --admins=Marcus [--port=24650] [--max-players=8] [--seed=N] [--data=DIR] [--world=NAME] [--autosave=S] [--new-world]`. Settings can also come from `DIR/server.cfg` (`key=value`: port, password, admins, max_players, day_minutes, autosave_s, world, seed, respawn_radius, linger_s, backpack_s; flags win). The world is saved in DIR (default `user://server`) under `worlds/NAME` (default `main`); `--seed` only applies to a new world; `--new-world` backs up the old one and starts over. **Stop it with `echo stop > DIR/control/stop.cmd`** (it saves and quits): Ctrl+C or `kill` end headless Godot at once without saving. Join from the game's title screen (Join server), or `-- --connect=host[:port] --name=N --pin=P --password=S` to skip the menu.
- **Screenshots with Forward+ here:** software Vulkan (`apt install mesa-vulkan-drivers`, lavapipe) under `xvfb-run -a -s "-screen 0 960x540x24"`, with `--resolution 960x540 -- --scenery --gfx=1 --shots=DIR` (about a minute; it is slow, so use small windows). After adding a `class_name` file, run `godot --headless --path . --import` once or the new class isn't found.
- **Screenshots of the menus and an online session:** run under `xvfb-run` with `--rendering-driver opengl3` and `--nettest=screens --shots=<dir>` (title/Join/Host), or `--nettest=b --shots=<dir>` as the second bot next to a server and an `a` bot.
- **Other flags:** `--gfx=0-3` (graphics quality for this run), `--version` (print "Dead Blocks X.Y.Z" and quit; update.sh uses it), `--server-mode` (simulate like the server), `--day-minutes=N` (default 30), `--radius=N` (chunk radius), `--no-spawns` (server: mobs only from `/spawn`, for tests), `--backpack-s=S` (server: backpacks fall apart after S seconds instead of 600, for tests), `--respawn-radius=M` (server: respawning without a bed lands within M m of the center, default 1000; 0 = the world spawn, which the multiplayer tests use), `--linger-s=S` (server: when a player's connection is lost, their character stays S seconds, default 60; 0 = not at all; leaving through the menu always takes it out at once), `--peer-timeout-ms=N` (server, tests: give up on a silent connection after N–2N ms instead of 15–30 s).

## Controls (M4.1)
- **E** interacts (opens the workbench, forge, campfire or Blood Forge you look at, picks up a bag); **I** opens your inventory with hand crafting. Both close their screen again, as does Esc. Right-click only places, eats and uses.
- Keys can be changed in Settings; the controller layout is fixed (`controls.gd` `PAD`). New UI must be focusable (`focus_mode` not NONE) and give a control the focus when it opens (`hud.focus_first`), so a controller can use it.

## Testing shortcuts in-game
- F6 (`/dusk`) skips to dusk or dawn; F7 (`/bloodmoon`) jumps to the Blood Moon (day 7, 19:57). They are admin commands: in Play solo and Host game you are the admin; on the Pi, the names in `server.cfg`.
- In chat (T), admins also have `/give item [n]`, `/spawn zombie|night|horde|runner|brute|crawler|screamer|spitter|boar [n]` (a type comes in tonight's mood, red-eyed during a Blood Moon), `/time HOUR`, `/clear` (removes every zombie and animal). Anyone can `/kill` (die and respawn; the pause menu's Die and Respawn does the same).

## Rules for server-side code
- **No physics space queries outside `_physics_process`** (raycasts, shape queries, `direct_space_state`). With physics on its own thread they fail; the test gate's ERROR-line check catches it.
- **Zombie code must not depend on processing order.** In `sim_tick`, read the world and the region's start-of-tick spatial hash only; queue block damage with `G.sim.queue_block_damage(...)` instead of calling `world.damage_block`; use the zombie's own `rng`, never `randf()`. The region-order test checks this.
- **Network messages are our own binary layouts in `net/protocol.gd`** (no RPCs or Synchronizers). Any layout change bumps `Proto.PROTOCOL`, and any release bumps `G.VERSION`: the server refuses other versions at login.
- **Online, the server owns blocks and inventories.** Change blocks on the server through `world.set_block` (it records the edit for clients); never change a client's world or inventory except from server messages or as a guess the server will confirm or undo. Drops and break times come from `Rules`, so solo and server agree.
- Server code runs without a HUD, textures, sounds or a local player (`G.hud`, `G.tex`, `G.sfx`, `G.player` are null): guard UI and sound calls (see `game._say` / `game._sound`).
- **Stopping goes through `NetServer.stop_server`** (control file `stop`, the Host game's watchdog): headless Godot dies instantly on SIGTERM/SIGINT without running any GDScript, so nothing can be saved from a signal. Anything new the server must remember goes into `save_world` (and, if it is per player, `_store_account` and `Save.player_json` / `load_players`).
- `ENetMultiplayerPeer.get_peer(id)` prints an ERROR for a peer that has gone; the server keeps its own `_live` set. `OS.is_process_running` only works for this process's own children.
